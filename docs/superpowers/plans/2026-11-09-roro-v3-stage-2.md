# RoRo v3 Tappa 2: Planner Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Uno strumento per planner: carica un Excel di prenotazioni accettate, ottiene un piano, valuta nuove richieste con l'Advisor, aggiorna il piano ed esporta.

**Architecture:** L'engine riceve un modulo `planning.py` per pianificare un insieme di unità tutte obbligatorie, con unità a bordo ferme ed esclusioni spiegate. Riusa il modello MILP esistente, dando a ogni metro caricato un peso che domina gli altri termini. Il server resta senza stato: il browser conserva nave, prenotazioni, piano e stato "a bordo", e li manda a ogni chiamata. L'Advisor riusa `advise` con una domanda futura basata sulle ipotesi del planner.

**Tech Stack:** come le tappe 0-1, più openpyxl.

**Spec:** `docs/superpowers/specs/2026-11-06-roro-v3-design.md` (§9.1 Planner, §9.11 regole di dettaglio, §7 stato e sicurezza, §11 tappa 2)

## Global Constraints

- Branch `v3-stage-2`. Nessun push su `v3` prima dell'ok del proprietario.
- `ScenarioParams()` e i risultati del gioco non cambiano.
- Excel: solo `.xlsx`, massimo 5 MB e 500 righe, macro mai eseguite. Errori riga per riga, tutti insieme, senza import parziale. Il file non viene salvato sul server.
- Colonne obbligatorie: `booking_id`, `customer`, `unit_type`, `length_m`, `weight_t`, `discharge_port`. Facoltative: `segment`, `is_reefer`, `rate_per_m`, `reefer_fee`, `height_m`, `axle_count`, `on_board`.
- Le accettate sono obbligatorie: nessuna viene esclusa in silenzio. Ogni esclusione ha un motivo leggibile.
- Unità `on_board` sempre ferme. Le altre possono muoversi; l'app elenca sempre le unità spostate.
- Nuova richiesta: prezzo per metro e segmento obbligatori.
- L'ipotesi di domanda è sempre visibile, con testo come `Assumption: high demand, 45% contract`.
- Il Planner usa spazio perso 15% di default; il gioco resta a 0.
- Primo piano entro 30 s e verdetto entro 5 s sulla demo da 600 m con 60 prenotazioni, su Cloud Run.
- Testo dell'app in inglese. `Planning estimate, not a loading computer.` resta visibile nel Planner.

## Review Focus

- Excel con righe vuote in fondo, intestazioni con spazi o maiuscole diverse, numeri scritti come testo ("13,6"): l'utente si aspetta che funzioni oppure un errore chiaro sulla riga giusta. Test in Task 2.
- Excel con più prenotazioni di quante ne stiano sulla nave: piano parziale, esclusioni ordinate con motivo, nessun crash né timeout oltre i 30 s. Test in Task 1 e Task 3.
- Unità segnata a bordo in una zona che con le nuove impostazioni (meno corsie, più spazio perso) non esiste più o non la contiene: messaggio chiaro, nessun 500. Test in Task 3.
- Nuova richiesta con lo stesso `booking_id` di una già presente: rifiutata con motivo. Test in Task 3.
- Sessione del Planner ricaricata dal browser con dati vecchi o danneggiati: la pagina parte vuota con un avviso, senza bloccarsi. Test in Task 5.

### Task 1: Pianificazione delle prenotazioni accettate nell'engine

**Files:**
- Create: `roro_yield/planning.py`, `roro_yield/demand.py`
- Modify: `roro_yield/optimizer.py` (`solve_optimal` accetta `deck: DeckState | None = None`)
- Test: `tests/test_planning.py`, `tests/test_demand.py`

**Interfaces:**
- Produces: `solve_optimal(scenario, time_limit_s=3, candidates=(), deck=None) -> Plan`. Con `deck`, le unità già nel deck sono costanti e il piano restituito contiene anche le loro posizioni. Il default lascia il comportamento identico.
- Produces: `PlanningResult(plan: Plan, excluded: list[tuple[str, str]], moved: list[str])` (dataclass frozen).
- Produces: `plan_accepted(vessel: Vessel, bookings: Sequence[Booking], previous: dict[str, Slot] | None = None, on_board: frozenset[str] = frozenset(), time_limit_s: float = 20) -> PlanningResult`:
  1. Le unità `on_board` sono messe nel deck alla loro posizione in `previous`. Se una non entra più, solleva `OnBoardConflict(booking_id, reason)`.
  2. Se `previous` copre tutte le altre e ognuna entra ancora al suo posto, restituisce quel piano senza spostamenti.
  3. Se `previous` copre tutte tranne quelle nuove, prova a inserire le nuove con `DeckState.best_slot` sopra il piano precedente; se entrano tutte, nessuno spostamento.
  4. Altrimenti risolve con `solve_optimal` su copie delle prenotazioni con `rate_per_m = METRE_WEIGHT` (1000), `reefer_fee = 0`, `handling_cost = 0`, impegno contrattuale 0, `deck` con le unità a bordo e `previous` come candidato. Così si massimizzano i metri caricati, e a parità di metri pesa la zavorra.
  5. `excluded`: per ogni unità non caricata, il motivo di `DeckState.why_not` sul piano finale, ordinato per lunghezza decrescente.
  6. `moved`: unità presenti sia in `previous` sia nel piano finale con posizione diversa.
- Produces: `expected_remaining(n_total: int, frac: float, contract_share: float) -> int` in `demand.py`: arrotonda `n_total * (1 - F(frac))`, con `F(f) = cs·min(f/0,7, 1) + (1-cs)·clip((f-0,2)/0,8, 0, 1)`, coerente con `CONTRACT_ARRIVAL` e `SPOT_ARRIVAL` del simulatore.
- Produces: `DEMAND_LEVELS = {"low": 0.75, "normal": 1.08, "high": 1.30}`, rapporto domanda/ponte, e `requests_for_level(level: str, usable_m: float) -> int` = `round(ratio * usable_m / 14.1)`. 14,1 m è la lunghezza effettiva media del mix del simulatore; Step 3 la ricava dai dati e aggiorna la costante se diversa.

### Task 3: API del Planner

**Files:**
- Create: `server/planner_api.py`
- Modify: `server/export_api.py` (sorgente `planner`), `server/main.py`
- Test: `tests/api/test_planner_api.py`

**Interfaces:**
- Consumes: `plan_accepted`, `OnBoardConflict`, `expected_remaining`, `requests_for_level`, `DEMAND_LEVELS` (Task 1); `PlannerBooking` (Task 2).
- Produces: `PlannerVessel` (Pydantic): `preset: "demo"|"ropax"|"shortsea"` più gli stessi campi nave e stabilità di `LabParams`, con `broken_stowage_pct` di default 0,15. `vessel_from(settings) -> Vessel` costruisce la nave come `generate_scenario`.
- Produces: `PlannerState{vessel: PlannerVessel, bookings: list[PlannerBooking] (max 500), placements: dict[str, str]}`.
- Produces: `POST /api/planner/plan` (corpo `PlannerState`) → `{job_id}`; risultato `PlannerPlan{placements: dict[str, str], excluded: [{booking_id, reason}], moved: [str], deck: DeckOut, kpis: {...}, revenue_known: bool}`. `revenue_known` è falso se qualche prenotazione caricata non ha prezzo.
- Produces: `POST /api/planner/move` (`PlannerState` + `booking_id`, `slot`) → `PlannerPlan` sincrono, oppure 422 col motivo di `DeckState`. Un'unità a bordo non si sposta: 422 `This unit is on board and cannot move.`
- Produces: `Demand{level: "low"|"normal"|"high", contract_share: float 0-0,9, spot_rate_multiplier: float 0,7-1,5, window_days: int 1-60 (default 14), hours_to_departure: float ≥ 0}`; `assumption_text(d) -> str`, per esempio `Assumption: high demand, 45% contract`.
- Produces: `POST /api/planner/advise` (`PlannerState` + `request: PlannerBooking` + `demand: Demand`) → `{job_id}`; risultato `verdict_out` più `assumption`. La vista dell'Advisor: deck con tutte le unità del piano attuale; `arrival_frac = clip(1 - hours/(window_days*24), 0, 1)`; parametri di domanda con `n_requests = requests_for_level(level, usable_m)` e `seed = NEUTRAL_SEED`; `index = 0`, `n_total = 1 + expected_remaining(...)`; impegno contrattuale 0. Richiesta senza `rate_per_m` o con `booking_id` già presente: 422.
- Produces: export `source: "planner"` con `state: PlannerState` e `plan_key: "planner"`; il PDF dichiara lo spazio perso e il numero di unità escluse.
