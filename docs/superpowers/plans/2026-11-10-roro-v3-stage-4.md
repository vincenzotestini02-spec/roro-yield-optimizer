# RoRo v3 Tappa 4: Spazio riservato per cliente Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Il planner tiene metri della nave per un cliente; quei metri restano liberi per lui finché il planner non rilascia la riserva, e piano, Advisor ed export ne tengono conto.

**Architecture:** Una `Reservation(customer, metres)` vale su tutta la nave. Il `DeckState` riceve le riserve e le rispetta nei controlli di fattibilità, con un motivo leggibile. Il modello MILP aggiunge una variabile di quota non usata per cliente e un vincolo globale sui metri; poiché l'Advisor e il Planner passano già il deck al modello, le riserve arrivano ovunque da lì. Il server e il Planner le aggiungono allo stato della sessione.

**Tech Stack:** come le tappe precedenti.

**Spec:** `docs/superpowers/specs/2026-11-06-roro-v3-design.md` (§9.5 spazio riservato, §11 tappa 4)

## Global Constraints

- Branch `v3-stage-4`. Nessun push su `v3` prima dell'ok del proprietario.
- Regola: metri caricati (con lashing gap) + quota riservata non ancora usata ≤ capacità utile della nave (dopo lo spazio perso). Il cliente consuma prima la propria quota; gli altri non possono usarla. La riserva vale su tutta la nave, non per zona.
- La riserva è un vincolo rigido finché il planner non la rilascia, anche contro una prenotazione accettata. In quel caso la prenotazione esclusa ha il motivo `space is reserved for <customer>`.
- Senza riserve, tutti i risultati restano uguali a prima.
- Il gioco e il Lab non cambiano: le riserve vivono nel Planner.
- Il nome cliente si confronta senza maiuscole e spazi ai lati.

## Review Focus

- Riserva più grande dello spazio utile della nave: 422 con motivo, nessun piano assurdo. Test in Task 3.
- Due riserve per lo stesso cliente scritto in modo diverso ("Nordfreight" e " nordfreight "): sono la stessa riserva, oppure il server rifiuta il doppione. Test in Task 3.
- Cliente riservatario con prenotazioni oltre la propria quota: la parte oltre la quota usa lo spazio libero comune, non quello di altri riservatari. Test in Task 1.
- Nuova richiesta di un cliente non riservatario quando resta solo spazio riservato: l'Advisor risponde che non entra, con il motivo della riserva. Test in Task 2.
- Sessione salvata prima di questa tappa (senza campo riserve): si apre come prima, senza riserve. Test in Task 4.

### Task 1: Riserve nel deck

**Files:**
- Modify: `roro_yield/models.py` (`Reservation`), `roro_yield/deck.py`
- Test: `tests/test_reservations.py`

**Interfaces:**
- Produces: `Reservation(customer: str, metres: float)` (dataclass frozen) e `customer_key(name: str) -> str` (minuscolo, senza spazi ai lati) in `models.py`.
- Produces: `DeckState(vessel, reservations: Sequence[Reservation] = ())`; `copy()` le conserva.
- Produces: `DeckState.reserved_left(customer: str | None = None) -> float`: metri riservati non ancora usati, di tutti i clienti tranne `customer`.
- Produces: `DeckState.usable_left_for(b: Booking) -> float`: metri che `b` può ancora usare = capacità utile − metri caricati − `reserved_left(b.customer)`, più la quota residua del suo cliente. Più precisamente: `b` entra solo se `used + len_b + reserved_left(b.customer) + max(0, quota_b − used_b − len_b) ≤ capacità`.
- Produces: `feasible_slots` restituisce `[]` se la regola sopra non vale; `why_not` restituisce `space is reserved for <customer>` (il cliente con la riserva più grande ancora libera) se è l'unico motivo.
- Produces: `DeckState.reservation_status() -> list[dict]`: per ogni riserva `{customer, metres, used, left}`.

### Task 2: Riserve nel modello, nel Planner e nell'Advisor

- Test: `tests/test_reservations_planning.py`

**Interfaces:**
- Consumes: `DeckState(vessel, reservations)`, `Reservation`, `customer_key` (Task 1).
- Produces: `build_model(...)` legge `deck.reservations` se `deck` è dato. Per ogni riserva crea `unused_c ≥ 0` e `unused_c ≥ quota_c − metri_del_cliente_già_sul_deck − Σ len·y` (prenotazioni del cliente); vincolo `Σ len·y + Σ unused ≤ capacità utile − metri già sul deck`. Senza riserve il modello è identico a prima.

- L'Advisor non cambia firma: la vista porta il deck, che porta le riserve.
